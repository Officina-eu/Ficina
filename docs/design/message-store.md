# Message store (design note)

`ficina-store` is where customer data comes to rest: mailboxes,
messages, flags, threads, and blob metadata on PostgreSQL, message
bytes in Garage (S3). It is the load-bearing crate — tenancy becomes
*structural* here, not conventional.

## Surface

- `Store` — the process-wide handle (a `PgPool` + a `BlobStore`). Its
  public API does **system** operations only: create/look-up tenants,
  run migrations. It exposes **nothing** about tenant-owned rows.
- `Store::for_tenant(TenantId) -> TenantStore` — the only door to mail
  data. A `TenantStore` carries its `TenantId` and issues every query
  with `tenant_id = $tenant` baked in. Mailboxes, messages, flags,
  threads, blobs, search, and ingestion all live here.
- Ids are opaque, random, URL-safe (`base64url(16 random bytes)`),
  generated by us — never a sequential integer crosses the API. A
  leaked id reveals nothing and cannot be incremented to a neighbour's.

## Errors

Typed (`thiserror`): `NotFound` (also what a *wrong-tenant* lookup
returns — never a distinct "forbidden" that would confirm existence),
`Conflict`, `TooLarge`, `Db`, `Blob`. Internal SQL/S3 errors never
reach a caller verbatim.

## Tenancy — by construction (the decision that outlives everything)

Every read and write is scoped to a tenant *because the type system
gives you no other shape to call*:

- You cannot query mail without a `TenantStore`.
- You obtain a `TenantStore` only via `Store::for_tenant(TenantId)`.
- A `TenantStore` holds its `TenantId` privately and interpolates it
  into every statement's `WHERE tenant_id = $1`. No public method takes
  a `tenant_id` argument; none takes an `Option<TenantId>`.
- A cross-tenant probe (tenant A asks for an id owned by B) matches
  zero rows under A's predicate → `NotFound`. Identical to a truly
  absent id: no existence oracle.

**Rejected alternative 1 — a `tenant_id` parameter on every call.**
Enforcement then lives in the caller's discipline: one forgotten
argument, or one `Option<TenantId>` that a code path leaves `None`, is
a cross-tenant leak that compiles. The wrong-tenant test suite would
have to cover every call site forever. Rejected: isolation must be
un-forgettable, and the handle pattern makes "forget the tenant"
unrepresentable.

**Rejected alternative 2 — Postgres Row-Level Security as the primary
line.** RLS is real and we may add it as defence in depth, but as the
*only* line it has failure modes we cannot accept as sole protection:
it is bypassed by the table owner / `BYPASSRLS` roles and by any
`SECURITY DEFINER` function, it depends on a per-connection
`SET app.tenant` that a pooled connection can leak across checkouts if
a reset is ever missed, and a policy that fails open on a mis-set GUC
is invisible until an audit finds it. We keep enforcement *in the
query text we control and test*, where a missing predicate is a
compile/test failure in our code, not a database configuration we hope
is loaded. RLS MAY be layered on later as belt-and-braces; it may not
be the only line.

## Schema & migrations (expand → migrate → contract)

Versioned SQL under `migrations/`, applied by `sqlx::migrate!()` at
startup and checked at compile time by the `query!` macros against a
committed offline cache (`.sqlx/`), so CI builds without a live DB.

Tenants run these in production, so every change is **expand → migrate
→ contract** across releases: add the new nullable column/table
(expand), backfill + dual-write (migrate), drop the old shape only once
nothing reads it (contract). No destructive migration ships in the same
release that starts depending on it.

Entities: `tenants`, `users`, `mailboxes` (hierarchical via
`parent_id`, with transactional `total`/`unread` counters), `threads`,
`messages` (metadata + parsed `Authentication-Results`: SPF/DKIM/DMARC
result columns, queryable), `mailbox_messages` (membership — a message
in many mailboxes, JMAP), `message_keywords` (JMAP keywords / IMAP
flags), `blobs` (content hash + size + refcount; bytes in Garage).
Every tenant-owned table carries `tenant_id` and a
`(tenant_id, …)`-leading index so the tenant predicate is always an
index seek (see the mailbox-listing `EXPLAIN` in the PR).

## Blobs

Content-addressed: the SHA-256 of the bytes is the id; the Garage key
is `<tenant_id>/<hash>`, so a tenant's blobs are physically prefixed by
its id and `TenantStore` only ever reads under its own prefix. Writes
go through one path (hash → store-if-absent → upsert `blobs` row with
`refcount += 1`); a byte ceiling is enforced on read as well as write
(the protocol skill's "bound the size on the wire", applied to S3).
Deletion is deferred: `refcount` reaching zero *marks* a blob for a
later GC sweep — we never delete on the delivery path. `BlobStore`
wraps the `object_store` abstraction, so the backend is swappable
without touching store code: `BlobStore::in_memory()` for fast
deterministic tests, `BlobStore::garage()` (S3) for real deployments.

## Ingestion & crash-safety

`TenantStore::ingest(user, raw, envelope, auth_results)`:

1. Parse headers (From/To/Subject/Message-ID/References/In-Reply-To/
   Date) + body.
2. **Write the blob to Garage first** (content-addressed).
3. In **one Postgres transaction**: thread the message (below), insert
   the `messages` row referencing the blob, add `mailbox_messages`
   membership, bump the mailbox counters, upsert the blob refcount, and
   update the search vector. Commit.

**Crash-safety choice — the blob wins the race; the DB commit is the
commit point.** If we crash after the blob write but before the
transaction commits, an *orphan blob* exists in Garage that no row
references. It is invisible to every tenant (no message row → not
listable, not readable) and is reclaimed by the blob GC (unreferenced
content). Nothing half-visible, nothing lost: the message was simply
not accepted, and the delivering side (SMTP 451 / the migration tool's
idempotent retry) sends it again. The alternative ordering — row first,
then blob — is rejected: a committed message row pointing at a
missing blob is a *visible* message that fails on read, i.e. real data
loss. Better an invisible orphan the GC eats than a visible hole.

Threading follows RFC 8621 §3 / RFC 5322 References: a message joins
the thread of an **earlier** message it references (via the
`In-Reply-To`/`References` message-ids we store); absent a reference
match it starts a new thread. We deliberately do **not** merge on base
subject alone — that bleeds unrelated same-subject conversations
together — so `threads.subject_base` is a display label, not a join
key. Two limitations are accepted and documented (`docs/interop.md`):
threading is **forward-only** (a reply delivered before its parent
starts its own thread and is not retro-merged), and same-subject
messages without references stay in separate threads. Property-tested:
reply chains converge to one thread; unrelated messages never merge.

## Out of scope (this milestone)

JMAP/IMAP endpoints (next session, on top of this), MIME body-part
extraction beyond best-effort text for search, blob GC *sweep*
execution (we mark; the sweep is a later job), and RLS (may be layered
later). Full-text search and the spool-migration tool are the approved
cut seams if the session runs long.
